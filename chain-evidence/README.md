# chain-evidence

A machine-readable record of every real transaction submitted while writing this
project's specification, whether or not the script it carried belongs to the generated
corpus under `vectors/`.

## Authored, not generated

Everything else this project ships is either generated and checked by rebuilding it, or
carried forward by a chain exercise that records what a node actually did. This record
is neither. It is transcribed by hand from `spec/06-chain-exercises.md` and its
neighbors, each value checked against what that document states. Most of the
submissions here predate the exercise automation that would otherwise have written them
as a vector's own `onchain` observation.

Nothing regenerates `observations.json`, and nothing should. There is no
`chain-evidence:build` script, and none should be added. An observation records what a
node did, and it cannot be recomputed: a hand edit that could not be told from a rebuild
would stop this file being evidence of anything. The same rule already governs a
vector's `onchain` array; see `spec/05-conformance.md`.

The other two files here, `record.md` and `scripts.json`, are derived from
`observations.json` by a script and checked against it on every build. The rule is about
which file an observation enters through, not about this directory.

## Format

`observations.json` carries a `formatVersion`, an `entryCount`, and an `entries` array.
Each entry is one submission: `network`, `accepted`, `txHash` when accepted, the
ledger's verbatim `error` when refused, and `demonstrates`, saying in the source's own
terms what the submission shows. `source` names the spec document and section a value
was transcribed from, so a claim here is always traceable back to where it was stated.

An entry that corresponds to a corpus vector carries that vector's `id` as `vectorId`.
`degenerate/empty-all`, `degenerate/empty-atleast-0`, `degenerate/empty-any`,
`threshold-matrix/atleast-0-of-3` and `degenerate/atleast-negative` are the five vectors
this applies to today; their own `onchain` arrays remain the authority the verifier's
contradiction check reads, and this record only points at them. An entry without a
`vectorId` exercised a protocol limit that no corpus vector represents, for example the
depth-ceiling and multisig-ceiling exercises, whose scripts are larger than anything the
corpus generates. `shape` then carries whatever the source states about that script or
transaction: `depth`, `keyCount`, `scriptBytes`, `transactionBytes`.

`cborHex`, matching `EncodingRecord.cborHex` and `ChainObservation.cborHex`, carries the
submitted transaction's raw bytes. It is populated on all 21 accepted entries and on none
of the refused ones. No value was transcribed: the spec prose the rest of this record was
built from never quotes transaction bytes, so each one was refetched from the chain by
transaction hash through Koios, which needs no API key.

What makes those bytes safe to carry is that they prove themselves. A transaction id is
blake2b-256 of the `transaction_body` bytes, so `checkTransactionBytes` in
`src/chain/evidence.ts` slices the body out of a stored `cborHex`, hashes it, and requires
the result to equal the `txHash` the entry already claims. That check runs offline in the
default suite. Every other field here was read off a document and has to be believed; this
one fails the build the moment it stops being the transaction it names.

A refused submission carries none, because it never reached a chain and so has no hash to
refetch it by. Those bytes exist only if a future exercise records them at submission
time, through `ChainProvider.submit`.

`referenceScript` appears on the two entries that spent against a script rather than
carrying it. A reference input names an output, and the script's bytes sit in whichever
earlier transaction created that output, which no amount of reading the submitted
transaction recovers. The field holds that creating transaction's `createdBy` hash,
`outputIndex`, `scriptHash` and `cborHex`, and is checked the same way: the bytes must
hash to `createdBy`, and the script in the named output must hash to `scriptHash`.

## The scripts a node has carried

`scripts.json` is the set of native scripts pulled out of those transaction bytes: 16
distinct byte strings across the 21 accepted submissions, deduplicated by bytes and keyed
by script hash. Each one records the CBOR exactly as a transaction carried it, the hash of
those bytes as received, which of the two standard encoders reproduce them, and the shape
it decodes to. It also records the corpus vector with identical bytes where there is one,
and every submission that carried it.

It exists because every other byte string this project tests its decoder against was
produced by this project. `vectors/` is generated by `src/generate/`, and the strings in
`test/unit/slot-range.test.ts` were written by hand to state a rule. Both are worth
having and neither is independent: an encoder and a decoder written together agree about
framing whether or not the framing is right, so a corpus round-trip establishes
self-consistency and stops there. These bytes were framed by other software and accepted
by a node. `test/unit/chain/observed-scripts.test.ts` is what holds the decoder to them.

Three of the entries are the reason it is worth having.

One script, `d66ed8e0`, is `all [ sig(k), before(18446744073709551615) ]`. A node accepted
it, and this library cannot decode it: 2^64-1 is the largest slot the CDDL admits and sits
far above `Number.MAX_SAFE_INTEGER`, so the AST cannot hold it exactly. Refusing is
correct, because the alternative is truncating and returning the wrong script hash, but it
means `decodable` is false on a script that is live on a real chain. `scriptHashFromCbor`
still works on it.

Two others, `b7e9fae9` and `cca7321c`, are the same 24-key `any`, funded and spent once at
each of its two addresses. They decode to the same script, differ in bytes, and hash
differently.

Like `record.md`, `scripts.json` is derived and never authored: `npm run
chain-evidence:scripts` writes it, `npm run chain-evidence:scripts:check` fails if the
committed file disagrees with what `observations.json` produces, and that check runs in
`npm run verify` and in CI. `src/chain/scripts.ts` does the extraction, reading the
transaction by byte offset and slicing rather than decoding and re-encoding, because
re-encoding can change the framing and so the hash. Regenerating twice from an unchanged
`observations.json` produces byte-identical output.

## Reading it as a document

`observations.json` is written for a program. `record.md`, in this same directory, is
the same record written for a person: every entry from `observations.json`, grouped by
the question it answers rather than by the order it sits in the JSON, with every
accepted transaction hash linked to that transaction on Cexplorer's preprod instance
and every refused entry showing the ledger's or the decoder's verbatim error in place of
the hash a refusal never has.

`record.md` is generated by `scripts/chain-evidence-record.ts` from `observations.json`
and nothing else, the same discipline `compat/aggregate.json` uses: `npm run
chain-evidence:record` writes it, `npm run chain-evidence:record:check` fails if the
committed file disagrees with what `observations.json` produces, and that check runs in
`npm run verify` and in CI. Regenerating it twice from an unchanged `observations.json`
produces byte-identical output; nothing in it is read from the clock.

`src/chain/evidence.ts` has the loader and the validators. `test/unit/chain/evidence.test.ts`
checks this file's own shape and its agreement with the five vectors it cross-references,
as part of the default offline suite. `npm run test:koios` checks every `txHash` here
against Koios and is opt-in, since it needs a reachable network. Koios needs no API key,
which is why this check uses it rather than the Blockfrost provider the exercise code
otherwise uses.

For the narrative behind each entry, read `spec/06-chain-exercises.md`,
`spec/03-satisfaction.md`, `spec/01-script-model.md` and `spec/07-encoding-divergence.md`.
This file does not repeat their tables; it only makes the same facts checkable by code.
